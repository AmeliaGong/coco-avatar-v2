# 线上一个来访者的会话发不出消息 —— 热修记录（2026-10-25）

> **分支**：`hotfix/chat-body-limit-2026-10-25`（从 `f9e4942` 切出 —— 那就是当时线上的 v70）
> **发布**：v71，镜像 `deployment-01M5SQDQDY0QA3S4H38C6K77B2`（2026-10-25T14:29:28Z）

## 现象

那位来访者在前端看到「抱歉，我现在遇到了一些技术问题。」
（`src/hooks/useChat.ts` 里那个 catch 的兜底文案），从 2026-10-24 15:37 UTC 起就发不出
任何消息。

## 原因

**前端每轮都把整段对话重发一遍**（`src/hooks/useChat.ts`：`chatMessages = [...messagesRef.current, 新的一句]`），
所以请求体的大小 ≈ 对话长度。

那个会话当时是 98 条消息、42,006 个字符；浏览器那一轮发出来的请求体是 **103,192 字节**，
比 `express.json()` 的默认上限（**102,400 字节 = 100kb**）多 792 字节。

于是 body-parser 在**解析阶段**抛 `entity.too.large`（`err.type === 'entity.too.large'`），
路由**根本没进不去**；错误中间件把它映射成 `400 {"error":"Invalid request body"}`；
前端的 `catch` 显示那句兜底文案。

两个容易走错的地方：

- **上限是在解析时生效的，不在路由里。** 只在路由里加判据一点用都没有 —— 必须把闸门本身挪走。
- **不是模型的问题。** 那一轮的单次 prompt 是 23,545 tokens，模型吃得很下；也不是过期
  （`/api/chat` 建的会话 `expires_at` 有值，但当时还没到）。

## 改了什么

1. **`/api/chat` 的请求体上限单独放宽到 1mb**（`server.js`：`MAX_CHAT_BODY_LIMIT`），
   其余端点仍是 100kb。**超限的语义不变**：仍是 `400 + {"error":"Invalid request body"}`
   （不给堆栈）—— 这条语义被 `tests/api.chat.test.js` 钉着。
2. **模型上下文的来源改成「库里已有的对话」**（`server.js` 的「上下文从哪来」+ `server/chatHistory.js`）。
   请求里带来的那份只用来「校验」与「取出这一轮新说的话」。
   - 库里那份是**完整的**（每轮的 user 与 assistant 都落库；前端刷新后也是从库里把对话
     拉回来显示的）；
   - 而且**不能被伪造** —— 以前拿一个 `conversation_id` 就能往模型上下文里塞假的历史；
   - **第一轮（库里还没有历史）仍然用请求里那份** ⇒ 首屏问候语那一轮的请求体与从前
     **逐字节相同**。
3. **history 加了长度上限**：`MAX_HISTORY_CHARS = 120000`（约 67k tokens）。
   history 以前**没有**上限（底座那份计划文档的「已知残留」里记着），唯一兜住它的是
   请求体那道 100kb —— 而那道闸门正在被移除 ⇒ 不另设一道，历史就会一直涨到模型不吃为止。
   丢的是**最旧**的轮次；**最后一条 user 消息永远留着**。
   教练分析那条路（`server/delivery/adminRoutes.js`）读的是整段对话，**不受影响**。
4. **前端只发「这一轮新说的话」**，不再重发整段对话 ⇒ 请求体不再随对话变长（这才是根因）。

## 与从前**有意**不同的地方（底座那份差异表的第 20 条）

- 多轮请求里，模型看到的是**库里的对话**，客户端重发的那份**不再**进上下文。
  ⇒ 从第二轮起，模型上下文里**没有首屏问候语**了（它从来没落过库，只活在前端的状态里）。
  这也让「同一条历史出现两次」不再可能。
- 上下文超过 120,000 字符时，最旧的轮次不再进上下文（会在服务端日志里打一行
  `chat history 已截断`）。

## 回滚注意

回滚到 v70 之后，**前端也会退回旧 bundle**（资源名带内容哈希，`index.html` 会指向旧的那份）。
只有「浏览器还开着、且已经加载了新 bundle、又不刷新」的窗口会受影响：那段时间里前端只发
「这一轮新说的话」，而 v70 的服务端把它当成全部上下文 ⇒ 模型会缺一段上下文（不影响可用性）。
v71 ⇒ v70 的回滚本身不需要改代码、不丢数据（本次没有 schema 变更）。

## 测试

`npm test`：543 → 544 全绿。新增 6 条，其中 6 条在**未修复**的 `server.js` 上全部失败
（用 `git stash push server.js` 验证过）：

- 请求体 103KB（那个会话的实际大小）→ 200，不再被挡在解析阶段；
- 103KB 的请求体被解析后，落到模型手里的是完整的那句话；
- 多轮：发给模型的是**库里重建的整段对话**，客户端重发的那份不重复；
- 客户端重发的历史里有伪造的助手回复 → 不进模型上下文；
- 超长的历史被裁到上限（丢最旧的，最后一条用户消息一定留着）/ 没超上限时一条都不丢；
- **事故回归**：照着她那个会话的形状（98 条消息、103KB 请求体）造一个，两种客户端都试。

线上核对（2026-10-25T14:29 之后）：

- 103,076 字节的请求体 → 进到路由里了（返回 `400 Unknown scenario`，因为核对时故意写了
  一个非法 scenario —— 这说明它在**解析阶段之后**，没有写库、没有花钱）；
- 1,200,000 字节的请求体 → 仍是 `400 {"error":"Invalid request body"}`（上限这道闸门还在）；
- 线上 bundle 是 `assets/index-TbKpXzN_.js`（本地构建产出的那一份）。

## 「差异 20」统一到这一份（2026-10-25 晚）

同一天，另一条分支上曾经有**第二套**「差异 20」：`history_mode` 协议
（客户端明说自己发的是全量还是增量）+ 全局 `express.json({limit:'1mb'})` +
客户端多一个 `src/lib/chatPayload.js`，而且**没有** history 长度上限。
两套编号相同、语义不同 ⇒ 下次合并会把「所有端点 1mb + 没有 history 上限」
带回线上，等于把底座守住的 100kb 闸门在所有端点拆掉。

⇒ **统一到本文档记的这一套**（`ef44713`），理由与逐条对比见
`docs/superpowers/plans/2026-10-24-coco-avatar-foundation.md` 的
「『差异 20』的**唯一**实现」一节。第二套连同它的 `src/lib/chatPayload.js`
与 `tsconfig` 的 `allowJs` 改动一并废弃。

⇒ 那一轮**还查清了一件事**：那条「用户发了消息、却没有任何回复」的记录，
是**模型那一轮失败**（服务端已经落了 user 行，assistant 行没有），**不是**
请求被 100kb 挡掉（那会在**解析阶段**被挡，连 user 行都不会有），也**不是**
进程崩了（fly 的机器事件里 14:24 前后没有重启）。

⇒ **还没做的**：首屏问候语的残留（从第二轮起模型看不见它）—— 修法有三条
（接受残留 / 给存量会话补行 / 服务端在重建上下文时补一句），**等 Coco 拍板**。
